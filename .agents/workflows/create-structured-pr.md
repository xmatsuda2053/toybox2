# create-structured-pr

## CRITICAL CONSTRAINTS

1. **PR作成前の絶対確認:**
   - いかなる理由があろうとも、ユーザーへの明示的な確認と承認（Approve）を得る前に、PRを作成（`gh pr create` / `pr-create`）してはなりません。
   - ドラフト生成後は必ずプレビューを提示し、処理を一時停止（Wait for User Input / Stop Here）してください。

2. **自律フェーズの制限:**
   - 「ドラフト提案」から「PR作成実行」へ移行する境界線は、エージェント自身の判断で越えてはなりません。ユーザーからの「作成してよい」「OK」「進めて」などの明示的な指示のみが次のフェーズへのトリガーとなります。

3. **ルールの優先順位:**
   - 本「ユーザー確認の実行」は、タスクの効率化や自動化に関する他のすべての指示に優先します。確認をスキップした作成は本Workflowの致命的なエラーとみなします。

4. **ベースブランチ（`main`）直接実行の禁止:**
   - カレントブランチがベースブランチ（`main`）の場合は PR を作成できません。必ずトピックブランチで作業およびコミットを行ってから実行してください。

5. **PRフォーマット規約の厳格遵守:**
   - **タイトル規約**:
     - 形式: `<type>(<scope>): <変更目的・成果の日本語要約> [(#<Issue番号>)]`
     - 使用可能タイプ: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`
     - 何を変更したかではなく、「何を解決・実現したか（目的・成果）」を簡潔に記述すること。
     - 関連 Issue 番号が存在する場合は末尾に `(#<Issue番号>)` を付与すること。
   - **本文フォーマット規約（4大セクション必須）**:
     - `## 概要`:
       - 対応する Issue（`Issue #XX の対応として、...`）
       - 背景、目的、主要な成果
     - `## 変更内容`:
       - 変更箇所・コンポーネント・パッケージ単位で番号付きリストでグループ化
       - **【全面禁止】差分（What）の逐条説明**: 単なるファイル変更や行の増減の羅列（「Aファイルを修正し、B行を追加しました」等）は厳禁。
       - **【必須記載】設計判断・理由（Why / Rationale）**: なぜその設計・アプローチを採用したのか、アーキテクチャの要点を記述。
     - `## 検証結果`:
       - 単体テスト（`npm test` の件数・成否）、型チェック（`npm run type-check`）、ビルド確認（`npm run build:...`）などの具体的な結果を明記。
       - ブラウザ実機や画面描画の手動確認結果（どのような挙動を確認したか）。
     - `## 関連 Issue`:
       - `Closes #XX` または `Fixes #XX`（GitHubのオートクローズキーワード）。

---

## Steps

### 1. リポジトリおよび差分コンテキストの調査
- スキル `repo-context-inspect` を PR モードで実行し、ブランチ差分、コミット履歴、関連 Issue、プッシュ状態を一括取得する。

```powershell
pwsh -File .agents/skills/repo-context-inspect/scripts/inspect-context.ps1 -Mode PR -BaseBranch "main"
```

- 取得結果（JSON）から以下を確認する:
  - `errorMessage` が存在する場合は、その内容を報告して処理を中断する（例: `main` 上での実行等）。
  - `prContext.existingPr`: 既にオープンしている同一ブランチの PR が存在する場合は、その URL とタイトルを報告し、新規作成を継続するかユーザーに確認する。
  - `prContext.hasUncommittedChanges`: 作業ツリーに未コミットの変更が存在する場合は、それらのファイルが PR に含まれない旨を警告し、コミット漏れがないか注意喚起する。
  - `prContext.commitCount`: Base〜Head 間のコミットが 0 件の場合は、「ベースブランチとの差分コミットが存在しません」と伝えて処理を中断する。
  - `prContext.relatedIssue`: 自動抽出された Issue の背景・目的・完了条件を確認し、PR 本文の生成に活用する。

### 2. PR 本文（Markdown）ドラフトの生成
- ステップ1で収集したコミット履歴、差分統計、関連 Issue 情報を統合し、以下のテンプレートに従ってドラフトを作成する。

```markdown
## 概要

Issue #<番号> の対応として、<何を解決・実現したかを簡潔に記述>。
<変更の背景、動機、および達成された主要な成果>

## 変更内容

1. **<コンポーネント/パッケージ名または主要変更領域>** (`<主要パス>`):
   - <設計判断や変更の要点（Why / Rationale）を箇条書きで記述>
   - <コードの逐条説明（行番号や単なる構文変更）ではなく、アーキテクチャや責務の意図を明確にする>

2. **<その他変更領域>** (`<主要パス>`):
   - <要点と設計理由>

## 検証結果

- `npm test`: <テスト実行結果・全テストパス状況>
- `npm run type-check`: <型チェック結果>
- `npm run build:...`: <ビルド結果・成果物サイズ等の確認>
- <実機/ブラウザ確認等の手動検証内容>: <確認した動作や画面挙動>

## 関連 Issue

Closes #<番号>
```

### 3. ドラフトの提示とユーザー承認待機（Wait for User Input / Stop Here）
- 生成した PR タイトル案および本文ドラフトを以下のフォーマットでユーザーに提示する。

```markdown
### Pull Request 提案プレビュー

- **PR タイトル案**: `<生成したタイトル>`
- **ベースブランチ**: `<prContext.baseBranch>` ← **ヘッドブランチ**: `<prContext.headBranch>`
- **対象 Issue**: [#<番号>] <Issue タイトル>
- **未プッシュコミット**: <prContext.unpushedCommitCount> 件（※作成承認時に自動プッシュされます）

#### 本文プレビュー
---
<作成した本文Markdown>
---

この内容で Pull Request を作成してよろしいですか？（修正点や変更希望があればお知らせください）
```

- **提示後、必ず「この内容で Pull Request を作成してよろしいですか？」と確認を求め、処理を一時停止（Wait for User Input）すること。ユーザーから明示的な承認を得るまでは、絶対に次のステップへ進んではならない。**

### 4. 安全な PR 作成の実行（Only After Explicit Approval）
- ユーザーから「OK」「進めて」「作成して」などの明示的な承認を得た場合のみ、スキル `pr-create` を用いて登録を実行する。
- 本文をスクラッチ領域の一時ファイル（UTF-8）に書き出す:
  - `<artifactDir>/scratch/pr_body.md`
- タイトルを一時ファイル（UTF-8）に書き出す:
  - `<artifactDir>/scratch/pr_title.txt`
- スキル `pr-create` のスクリプトを実行する（未プッシュコミットがある場合に備え `-AutoPush` を付与）:

```powershell
pwsh -File .agents/skills/pr-create/scripts/create-pr.ps1 `
  -TitleFile "<タイトルファイルの絶対パス>" `
  -BodyFile "<本文ファイルの絶対パス>" `
  -Base "<ベースブランチ名>" `
  -AutoPush
```

### 5. 完了報告
- スクリプトの返却 JSON を確認し、作成完了結果をユーザーに報告する。

```markdown
### Pull Request 作成結果: 成功
- **PR**: [#<番号>] <タイトル>
- **URL**: <PR URL>
- **ブランチ**: `<headBranch>` -> `<baseBranch>`
- **ステータス**: 作成完了
```
