# git-commit

## CRITICAL CONSTRAINTS
1. **コミット前の絶対確認:**
   - いかなる理由があろうとも、ユーザーへの明示的な確認と承認（Approve）を得る前に、変更をコミット（Commit）してはなりません。
   - コードの生成や修正が完了した段階で、必ず「提案内容の提示」と「確認を求めるメッセージ」を出力し、処理を一時停止（Wait for User Input）してください。

2. **自律フェーズの制限:**
   - タスクが「提案」から「反映（コミット）」へ移行する境界線は、エージェント自身の判断で越えてはなりません。ユーザーからの「コミットして良い」という明示的な指示（テキスト入力や承認ボタン）のみが次のフェーズへのトリガーとなります。

3. **ルールの優先順位:**
   - 本「ユーザー確認の実行」は、タスクの効率化や自動化に関する他のすべての指示に優先します。本ルールを無視したコミットは、Workflowの致命的なエラーとみなします。

## Steps

1. **Get Context, Current Branch, and Staged Diff**
   - 以下のコマンドを実行し、「現在のブランチ名」と「ステージングされている変更（diff）」を取得してください。
     - `git branch --show-current`
     - `git diff --cached`
   - **例外処理**: もしステージングされている変更が存在しない場合（diffが空の場合）は、メッセージの生成を行わず、「コミット対象がステージングされていません。`git add` を行ってから再度実行してください」と伝えて処理を終了してください。
   - **コンテキスト情報の確認**:
     - ブランチ名（例: `feature/32-improve-git-commit-workflow`）や直前の対話履歴から、対応中の **Issue番号** や **作業目的・要求背景** を把握してください。
     - 必要に応じて、Issue の背景・目的（`gh issue view <issue-id> --json title,body` 等）を参照し、「なぜこの修正を行ったのか」の背景情報を補完してください。
   - ※未ステージングのファイルや、作業スペースのその他の状態は完全に無視してください。

2. **Generate Message in Japanese (Focus on "Why", Not "What")**
   - ステップ1で取得した情報をもとにコミットメッセージを生成します。その際、以下の**厳格なルール**をすべて遵守してください。

   - **言語と固有名詞の維持**:
     - メッセージの要約および詳細文は、**必ずすべて日本語**で記述すること。
     - プレフィックス、ファイル名、パス、関数・変数名などの英単語は、翻訳せず**そのまま英語で維持**すること。
   
   - **フォーマット**:
     - 1行目: `<type>: <変更目的・成果の日本語要約> [(#<Issue番号>)]`
       - **使用可能なタイプ（Type）**: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`
       - 何を変更したかではなく、「何を解決・実現したか（目的・成果）」を簡潔に記述すること（60文字以内）。
       - ブランチ名やコンテキストに対応する Issue 番号が存在する場合は、末尾に `(#<Issue番号>)` を付与すること。
     - 2行目: **必ず空行**を入れてください。
     - 3行目以降: **変更理由と背景・設計判断（Why）** を記述（100～200文字程度）。

   - **本文（3行目以降）の厳格な記述規約**:
     - **【全面禁止】差分（What）の逐条説明**:
       - `git diff` を見れば自明な「〇〇行目を削除して△△を追加した」「AファイルでBを呼び出すようにした」等のコードレベルの変更内容を文章でなぞるだけの記述は**厳禁**とします。
     - **【必須記載】変更理由・動機（Why）**:
       - なぜこの変更が必要だったのか（どのような課題、要求、不具合、設計上の問題があったのか）。
     - **【必須記載】設計判断・方針の理由（Why this approach / Rationale）**:
       - なぜそのアプローチ・設計を採用したのか（責務分離、保守性向上、パフォーマンス、安全性の確保など）。

   - **記載例（Good / Bad）**:
     - ❌ **Bad（コード変更内容をなぞっただけの説明）**:
       > `app-root.ts` から Menu ペインのコードを削除し、`pane-menu.ts` を新規作成しました。`pane-menu.scss` でスタイルを定義し、`app-root` で import して呼び出すようにしました。
     - ⭕ **Good（なぜそうしたかの理由・背景・設計意図）**:
       > `#30` に対応し、`app-root` の肥大化防止と各ペインの責務分離を図るため、Menu ペインを独立したコンポーネントとして切り出しました。サイドパネル開閉トグルボタンやアイコン表示のロジック・スタイルを局所化することで、保守性と単体テストの独立性を高めています。

3. **Present Proposal and Request Approval (Stop Here)**
   - 生成したコミットメッセージのプレビューと、コミット対象（ステップ1の変更ファイル一覧など）をユーザーに提示してください。
   - 提示後、**「この内容でコミットを実行してよろしいですか？ (Yes/No)」と必ずユーザーに確認を求め、処理を一時停止（Wait for User Input）してください。**
   - ユーザーから明示的な承認（例: 「ok」「yes」「進めて」「コミットして」など）を得るまでは、絶対に `git commit` コマンドを実行してはなりません。

4. **Execute Commit (Only After Explicit Approval)**
   - 承認を得た場合のみ、以下の形式でコミットを実行してください。
     ```bash
     git commit -m "<1行目のタイトル>" -m "<3行目以降の本文>"
     ```
   - コミット完了後、`git log -1` の結果を提示して処理を完了してください。
