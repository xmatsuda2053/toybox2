# git-commit

## CRITICAL CONSTRAINTS
1. **コミット前の絶対確認:**
   - いかなる理由があろうとも、ユーザーへの明示的な確認と承認（Approve）を得る前に、変更をコミット（Commit）してはなりません。
   - コードの生成や修正が完了した段階で、必ず「提案内容の提示」と「確認を求めるメッセージ」を出力し、処理を一時停止（Wait for User Input）してください。

2. **自律フェーズの制限:**
   - タスクが「提案」から「反映（コミット）」へ移行する境界線は、エージェント自身の判断で越えてはなりません。ユーザーからの「コミットして良い」という明示的な指示（テキスト入力や承認ボタン）のみが次のフェーズへのトリガーとなります。

3. **ルールの優先順位:**
   - 本「ユーザー確認の実行」は、タスクの効率化や自動化に関する他のすべての指示に優先します。本ルールを無視したコミットは、Workflowの致命的なエラーとみなします。

## Steps

1. **Get Current Branch Name and Staged Diff**
   - 以下のコマンドを実行し、「現在のブランチ名」と「ステージングされている変更（diff）」を取得してください。
     - `git branch --show-current`
     - `git diff --cached`
   - **例外処理**: もしステージングされている変更が存在しない場合（diffが空の場合）は、メッセージの生成を行わず、「コミット対象がステージングされていません。`git add` を行ってから再度実行してください」と伝えて処理を終了してください。
   - ※未ステージングのファイルや、作業スペースのその他の状態は完全に無視してください。

2. **Generate Message in Japanese**
   - 取得した `git diff --cached` の内容を元に、コミットメッセージを生成します。その際、以下の**厳格なルール**をすべて遵守してください。

   - **言語と固有名詞の維持**:
     - メッセージの要約および詳細文は、**必ずすべて日本語**で記述すること。
     - プレフィックス、ファイル名、パス、関数・変数名などの英単語は、翻訳せず**そのまま英語で維持**すること。
   
   - **フォーマット**:
     - 1行目: `<type>: <日本語の要約>`
       - **使用可能なタイプ（Type）**: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`
     - 2行目: **必ず空行**を入れてください。
     - 3行目以降: ステージングした修正内容の概要や変更理由（100～150文字程度）。
     - ※ブランチ名に課題番号やID（例: `#123`, `TASK-01` 等）が含まれている場合でも、指定がない限り要約のプレフィックスや本文に自然な形で反映するか、必要に応じて含めてください。

3. **Present Proposal and Request Approval (Stop Here)**
   - 生成したコミットメッセージのプレビューと、コミット対象（ステップ1の変更ファイル一覧など）をユーザーに提示してください。
   - 提示後、**「この内容でコミットを実行してよろしいですか？ (Yes/No)」と必ずユーザーに確認を求め、処理を一時停止（Wait for User Input）してください。**
   - ユーザーから明示的な承認（例: 「ok」「yes」「進めて」「コミットして」など）を得るまでは、絶対に `git commit` コマンドを実行してはなりません。

4. **Execute Commit (Only After Explicit Approval)**
   - 承認を得た場合のみ、以下の形式でコミットを実行してください。
     ```bash
     git commit -m "<1行目のタイトル>" -m "<3行目以降の本文>"
     ```
   - コミット完了後、`git log -1` の結果を提示して処理を完了してください。
