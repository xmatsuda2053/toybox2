# Refactor Executor Workflow (`/refactor-executor`)

## 目的

`_memo/refactoring-execution-plan.md`（段階的実行計画書）に基づき、アーキテクチャのレイヤ・責務単位でグルーピングされたフェーズごとに、**「4大観点の事前合意 → Issue作成 → ブランチ作成 → ユーザー許可制TDD → 品質ゲート実測（refactor-verify） → コミット & PR作成 → 計画書更新」** の標準8ステップサイクルを安全かつ確実に反復実行する。

単発タスクの無計画な改修やコード破壊を防ぎ、次回以降のリファクタリングでも完全に均一な作業粒度・安全性・品質記録を担保する。

---

## CRITICAL CONSTRAINTS（厳格制約）

1. **フェーズ着手前の事前合意（4大観点の必須提示）**:
   - いかなる場合も、ユーザーとの対話形式による事前検討および合意形成（Approve）を経る前に、コード変更（プロダクションコード・テストコード問わず）を開始してはならない。
   - 事前説明には、以下の **4つの観点** を必ず網羅して提示すること：
     - ① **現状の問題点**: 具体的にどのような重複や設計課題が生じているか
     - ② **なぜその方針としたのか（設計判断の理由・Why）**: クラス設計、抽象化、継承や射影等のアプローチを採用する根拠
     - ③ **修正の効果**: 重複行数・トークンの削減、保守性・コード凝集度の向上、外部利用側への影響範囲
     - ④ **将来的な拡張性の有無**: 要件変更、プロパティ追加、新エンティティ追加時にどう安全に拡張できるか

2. **自律フェーズ移行の制限（ユーザー確認の絶対遵守）**:
   - 「検討提案 → Issue作成」「TDD Red → 実装（Green）」「コミット案提示 → コミット実行」「PR案提示 → PR作成」の各境界線は、エージェント自身の判断で越えてはならない。ユーザーの明示的な指示（「OK」「進めてください」等）のみが次のステップへのトリガーとなる。

3. **Issue へのコンテキスト保護（バックログ詳細の転記）**:
   - `.agents/refactor-backlog.json` は Git 管理外であるため、将来 Issue やコミットから経緯を追跡できるよう、対象となるバックログ項目の詳細情報（ID、対象ファイル・行、重複行数・トークン数、診断サマリー）を Issue 本文の「補足情報」セクションに必ず転記すること。

4. **ユーザー許可制 TDD の徹底**:
   - 🔴 Red（テスト作成・失敗報告）→ ユーザー承認待機 → 🟢 Green（実装）→ 🔵 Refactor を厳守する。既存テストの破壊（デグレード）はゼロを維持すること。

5. **品質ゲート実測と検証結果の PR 明記**:
   - スキル `refactor-verify` を実行し、単体テスト・型チェック・コード重複（jscpd）・スタンドアロンビルドの全合格を実測数値で確認し、PR 本文の「検証結果」に明記すること。

6. **台帳保全と終端フェーズでの一括記録**:
   - リファクタリング完了による台帳レコードの削除や全置換再生成は**厳禁**とする。全フェーズ完了時（終端フェーズ）に、既存の `.agents/refactor-backlog.json` を完全に保全した上でインプレース更新し、プロセス追跡データ（`execution` オブジェクト）を正確に記録すること。

## ワークフロー手順（標準8ステップサイクル）

### 前提確認

1. `_memo/refactoring-execution-plan.md` を読み込む。
2. 「全体進捗ステータス管理」テーブルを参照し、未着手の最初のフェーズ（例: Phase 1）を特定する。
3. `git status` を実行し、未コミットの変更が存在しないクリーンな状態であることを確認する。

---

### Step 1: フェーズ詳細検討と合意形成（4大観点の提示）

1. 特定したフェーズの計画内容（対象アイテム、対象ファイル、課題と設計方針、検証方法）を整理する。
2. ユーザーへ以下の **4大観点** を構造的に提示し、対話形式で方針を検討・合意する：
   - ① **現状の問題点**
   - ② **なぜその方針としたのか（設計判断の理由・Why）**
   - ③ **修正の効果**
   - ④ **将来的な拡張性の有無**
3. **ユーザーの明示的な承認（「OK」「この方針で進めてください」等）を待機する。**

---

### Step 2: Issue 作成（`/create-structured-issue`）

1. ワークフロー `/create-structured-issue` に従い、Issue 本文ドラフトを作成する。
2. **コンテキスト保護**: 本文の「補足情報」セクションに、該当する `.agents/refactor-backlog.json` のアイテム情報（ID、重複行、トークン、診断サマリー）を漏れなく転記する。
3. ユーザーへドラフトを提示し、承認を得た後にスキル `issue-create` で Issue を作成する。
4. 作成された Issue 番号（例: `#55`）を控える。

---

### Step 3: 作業ブランチの作成

1. `main` ブランチを最新状態（`git pull origin main`）に同期する。
2. スキル `create-branch-from-issue` 等を用いて、Issue 番号と要約スラッグに基づいた作業ブランチを作成・チェックアウトする：
   ```powershell
   git checkout -b refactor/<issue-id>-<slug>
   ```

---

### Step 4: ユーザー許可制 TDD サイクル

プロジェクトルール第6項に基づき、TDD サイクルを進行する：

1. **🔴 Red（テスト作成・失敗報告）**:
   - 新設クラス・ヘルパーの振る舞い、または既存挙動を担保するユニットテスト（`*.test.ts`）を作成する。
   - `npm test -- <test_file>` を実行し、テストが意図通り失敗（または新規追加）することを確認する。
   - 失敗結果（または新規テスト内容）をユーザーへ報告し、**実装進行の許可が出るまで待機する（一時停止）**。
2. **🟢 Green（実装）**:
   - ユーザーから明示的な許可を得た後、テストをパスさせるための最小限の実装（基底クラス抽出、重複解消、エイリアス化等）を行う。
   - `npm test -- <test_file>` を実行し、All Green を確認する。
3. **🔵 Refactor（整理・最適化）**:
   - コードの可読性・構造を整理する（公開インターフェースや振る舞いは維持）。

---

### Step 5: 4大品質ゲートの検証（`refactor-verify`）

スキル `refactor-verify` の実測スクリプトを実行し、品質基準を判定する：

```powershell
pwsh -File .agents/skills/refactor-verify/scripts/verify-refactor.ps1 -TargetApp "apps/stepnote"
```

以下の合格基準をすべて満たすことを確認する：
- [PASS] Unit Tests: 失敗 0 件（`regressions_detected: 0`）
- [PASS] Type Check: エラー 0 件
- [PASS] Code Duplication (jscpd): プロダクションコード重複 0 件（または該当フェーズ対象の重複が解消されていること）
- [PASS] Standalone Build: 単一 HTML 出力成功

※ エラーが出た場合は自己修復ループ（最大3回）で修正し、解決しない場合はロールバックして報告する。

---

### Step 6: コミット & リモート Push（`/git-commit`）

1. 変更ファイルをステージングする：
   ```powershell
   git add <target_files>
   ```
2. ワークフロー `/git-commit` に従い、Why（改善理由・設計判断・効果）を明記したコミットメッセージドラフトを提示する。
3. ユーザーの明示的な承認を得た後、コミットを実行する。
4. 作業ブランチをリモートへ push する：
   ```powershell
   git push -u origin refactor/<issue-id>-<slug>
   ```

---

### Step 7: Pull Request 作成 & マージ（`/create-structured-pr`）

1. ワークフロー `/create-structured-pr` に従い、PR ドラフトを作成する。
   - 本文末尾に `Closes #<Issue番号>` を記載する。
   - 「## 検証結果」セクションに、Step 5 で取得した `refactor-verify` の実測値（テスト通過件数、型エラー0件、重複ブロック解消、ビルドサイズ等）を明記する。
2. ユーザーへドラフトを提示し、承認を得た後にスキル `pr-create` で PR を作成する。
3. PR のマージ完了後、ローカルの `main` ブランチに切り替えて最新化（`git pull origin main`）する。

---

### Step 8: 実行計画書のステータス更新

1. `_memo/refactoring-execution-plan.md` の「全体進捗ステータス管理」テーブルを更新する：
   - 該当フェーズのステータスを `完了` に更新。
   - `Issue` 列、`PR` 列、`完了日` 列、`備考・メモ` 列に実績を記入。
2. 更新内容をコミット（`docs: 実行計画書の Phase X 完了ステータスを更新`）し、push する。
3. 次のフェーズへ進むか、または終端フェーズへ進むかをユーザーに確認する。

---

## 終端フェーズ（Phase 5等: 全体検証と台帳一括更新）の特別手順

計画書に定義された全フェーズのコード改修が完了した後の最終フェーズでは、以下の手順を実行する：

1. **全体一括実測（`refactor-verify`）**:
   - `pwsh -File .agents/skills/refactor-verify/scripts/verify-refactor.ps1` を実行し、リポジトリ全体の品質メトリクスを出力。
2. **バックログ台帳のインプレース安全更新（台帳保全）**:
   - 再監査スクリプトによる台帳全置換は**厳禁**。
   - 既存の `.agents/refactor-backlog.json` の該当タスク（今回完了した全アイテム）をインプレースで `status: "completed"` に更新。
   - 各タスクの `execution` オブジェクトに、完了実績（完了日、PR番号、Issue番号、コミットハッシュ、テスト件数、実測後メトリクス `metrics_after`）を正確に記録・保存する。
3. **実行計画書の最終完了記録**:
   - `_memo/refactoring-execution-plan.md` の全フェーズを「完了」とし、全体の完了報告を行う。
