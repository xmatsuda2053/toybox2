# モノレポ共通開発・品質予防規約（Common Rules & Implementation Prevention）

## 適用スコープ（Scope）

- **対象**: モノレポ内のすべてのアプリケーション（`apps/*`）および共有パッケージ（`packages/*`）のコード実装・改修作業に適用する。
- **位置づけ**: 本規約は、リポジトリ全体に適用される「基盤品質・設計予防規約」である。各アプリケーション固有のアーキテクチャやレイアウト規約（例: `code-style-stepnote.md`）は、本規約を継承・前提として策定される。

---

## 1. 基本設計思想：機能実装時における品質予防原則

- **完成度100%の時期尚早な抽象化を避け、明白な悪手をゼロにする**:
  - コンポーネント等の小さな単位での局所的な最適解と、機能全体の最適解は異なる。新機能実装の初期段階（TDD の 🟢 Green 実装等）で、過度な共通化（過剰なDRY）や無理な共通コンポーネント化を急ぐ必要はない。
  - 一方で、**「過去に繰り返し発生した、単一ファイル・単一コンポーネント内で防ぐべき明白な悪手」**は、初期実装の時点で確実に予防すること。
  - これにより、機能完成後に巨大なリファクタリングIssueが多発する事態を防止し、開発全体のサイクルタイムと保守負荷を最小化する。

---

## 2. TypeScript / Web Components 実装規約

### 2.1 関数の行数上限（50行）と認知的複雑度（15以下）の事前遵守
- **サブレンダーメソッドへの分割**:
  - `render` メソッド等の肥大化を最初から防ぐため、UIブロックや論理単位ごとにサブレンダーメソッド（例: `renderHeader()`, `renderItemList()`, `renderActionButtons()`）へ責務を小さく分割すること。
  - 単一関数の行数は **50行以内**（ESLint `max-lines-per-function` 制約）を厳守する。
- **ガード節（早期リターン）による平坦化**:
  - `if` 文や `switch` 文のネストによる認知的複雑度のインフレを避け、関数の先頭でガード節（早期リターン）を用いてフラットな制御構造を維持すること。
  - 関数の認知的複雑度は **15以下**（ESLint `sonarjs/cognitive-complexity` 制約）を厳守する。

### 2.2 UIとロジック（純粋関数）の即時分離
- **DOM・コンポーネント非依存ロジックの抽出**:
  - 文字列フォーマット、構文挿入・装飾、数値・日付計算、フィルタリング・ソート、DOM/ASTトラバースなどの処理を Web Component クラス内に直接インライン実装しないこと。
  - 最初から同一ディレクトリ配下の `*.utils.ts` や共通パッケージ（`packages/utils`）へ純粋関数（Pure Function）として抽出し、DOMシミュレータに依存しない軽量な単体テスト（Vitest）をセットで作成すること。

### 2.3 コントローラー購読ボイラープレートの標準化
- **Reactive Controller 接続パターンの統一**:
  - Web Components と Reactive Controller（状態管理・DBクエリ等）を連携させる際、手動でイベントリスナーやコールバックを個別登録して重複を作らないこと。
  - プロジェクト内で確立された共通購読パターンや Mixin（例: `bindControllerSubscriber` 等）を使用し、ボイラープレートを統一すること。

### 2.4 型安全性の徹底（`any` の完全禁止）
- **仮置き `any` の排除**:
  - 機能実装を急ぐ目的であっても、`any` 型や危険な型アサーション（`as any`）を使用してはならない。
  - ドメイン型、モデル型、または利用ライブラリ（Lit, CodeMirror, unified, Dexie 等）の公式型定義を最初から正しくインポート・定義すること。

## 3. SCSS / スタイリング規約

### 3.1 カラー直値（Hex / RGB / RGBA）の完全禁止
- **デザイントークン（CSSカスタムプロパティ）の参照**:
  - SCSS ファイル内にカラーコード（例: `#ffffff`, `#1f2328`, `rgba(...)`）を直接ハードコードすることは全面的に禁止する。
  - 色、背景、枠線、シャドウは、初期実装時から必ず共通トークン定義（`src/styles/tokens.scss`）に定義されたセマンティックトークン（`var(--wa-...)`, `var(--stepnote-...)`）を参照すること。
  - これにより、ダークテーマ切替時の配色不備やトークン化手戻りを未然に防止する。

### 3.2 既存共通 Mixin の必須利用
- **確立されたパターンの再発明禁止**:
  - 汎用レイアウトやUIパターンを書く際は、個別に CSS プロパティを並べるのではなく、`src/styles/mixins.scss` 等に定義済みの共通 Mixin を必ず利用すること。
    - **レイアウト**: `@include flex-center;`, `@include flex-between;`, `@include text-ellipsis;`
    - **スクロールバー**: `@include custom-scrollbar;`
    - **ベースリセット**: `@include box-sizing-reset;`
    - **コンポーネント共通**: 各アプリ・ペインの共通 Mixin（例: `@include pane-host-layout;`, `@include dialog-common;`, `@include dialog-dark-theme;`）
- **`@extend` の完全禁止**:
  - Web Components / Shadow DOM 環境において、`@extend` はコンポーネント境界を越えた共有ができずカスケード崩壊の原因となるため全面的に禁止する。パターンの共通化には必ず `@mixin` を使用すること。

### 3.3 `!important` の初期完全禁止
- **詳細度設計の厳守**:
  - スタイルが当たらない等の理由で `!important` を宣言することを全面的に禁止する。
  - Shadow DOM のカプセル化および適切なセレクタ詳細度設計によってスタイルを制御すること。

### 3.4 フラットな簡易BEMセレクタ設計
- **セレクタネストの抑制**:
  - HTMLツリー構造を過度に模倣した深いネストは避け、セレクタのネストは原則として **1階層**（擬似クラス・擬似要素や状態クラスを除く）に抑えること。
  - セレクタ命名には「簡易BEM記法（`.block__element--modifier`）」を採用し、タグ直接指定（`div`, `button` 等）や曖昧なクラス名を排除すること。

### 3.5 テーマ切替トランジションの必須適用
- **滑らかなテーマ遷移の保証**:
  - 新規コンポーネント作成時は、コンポーネントの `:host` や背景・文字・境界線を持つ主要要素に対し、共通 Mixin `@include theme-transition;`（またはトークン `var(--stepnote-transition-theme)`）を必ず指定すること。

## 4. 静的解析ツールによる定量的品質ゲート

リファクタリングで培った客観的・定量的診断手法を活用し、実装完了時（ワークフローの「品質検証フェーズ」）において以下のチェックを実行する。

全く同一パターンのリファクタリングIssueの発生を防ぐため、以下の基準をクリアしていることを確認すること。

| 検査対象 | 検証コマンド / ツール | 合格基準（定量的目標） |
| :--- | :--- | :--- |
| **関数行数** | `npm run lint` | 新規・変更関数の行数が **50行以内** であること（ESLint 警告 0 件） |
| **認知的複雑度** | `npm run lint` | 新規・変更関数の認知的複雑度が **15以下** であること（ESLint 警告 0 件） |
| **型安全性** | `npm run lint`<br/>`npm run type-check` | 不要な `any` 使用が 0 件、かつ TypeScript 型エラーが 0 件であること |
| **CSS構文違反** | SCSS静的チェック | `!important`, `@extend` の使用が 0 件であること |
| **カラー直値** | SCSS走査 / リント | 新規SCSS内で Hex / RGB / RGBA 直値が 0 件（トークン参照）であること |
| **コード重複** | `jscpd` | 他ファイルからの明らかなブロックコピペ（10行以上）が存在しないこと |
| **リグレッション** | `npm test`<br/>`npm run build:stepnote` | 既存単体テストが全件パス、かつ単一 HTML ビルドが成功すること |
